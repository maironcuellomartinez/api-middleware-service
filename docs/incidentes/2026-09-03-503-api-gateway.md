# Postmortem: 503 sostenido en api-gateway

| | |
|---|---|
| **Servicio afectado** | `api-middleware-service` → `api-gateway` |
| **Ventana del incidente** | 2026-09-03, ~04:14–08:1x UTC (~4h) |
| **Síntoma observado** | HTTP 503 sostenido en las llamadas a `api-gateway` |
| **Detección** | Script de diagnóstico manual (una petición cada ~3 min, iterando por rango de fecha) |
| **Resolución** | Automática — sin deploy ni cambios de código en este repositorio |

## Resumen

Durante ~4 horas, las peticiones que `api-middleware-service` reenvía a `api-gateway` devolvieron **503 Service Unavailable** de forma sostenida, con recuperación automática.

La causa raíz fue una caída real de **api-gateway** (su propio Apache reenviando la página de mantenimiento por defecto) — **no** el circuit breaker, **no** el bulkhead HTTP, y **no** el proceso de `api-middleware-service`, que permaneció sano y respondiendo durante toda la ventana.

## Línea de tiempo

- **04:14–08:1x UTC** — Un script propio, apuntando a `api-middleware-service` (no directo a `api-gateway`), ejecuta una petición cada ~3 min iterando por rangos de fecha. Cada intento recibe `status=503` con `duration≈260–275ms` — respuesta rápida y consistente, no un cuelgue.
- **Análisis** — El `message` del error no coincide con ningún mensaje propio del código: se descartan los tres orígenes de 503 conocidos (circuit breaker, bulkhead, guard) porque ninguno produce el body observado (una página HTML completa, no un JSON propio). Ver [Hipótesis descartadas](#hipótesis-descartadas).
- **Confirmación** — El body es la página 503 por defecto de Apache/httpd: el texto *"temporarily unable to service your request due to maintenance downtime or capacity problems"* es el `ErrorDocument` estándar de Apache, coincidiendo con el proxy que Apache mantiene delante de `api-gateway`.
- **~08:1x UTC** — Recuperación automática: las respuestas vuelven a `200 OK` sin cambios en `api-middleware-service`, consistente con que el backend real detrás del Apache de `api-gateway` volvió a estar disponible.

## Cadena de la petición

```
Script de diagnóstico          api-middleware-service            api-gateway (Apache)
(cada ~3 min, por fecha)  -->   bulkhead OK · circuit breaker  -->   [FALLO]
                                clasificando · responde en           devuelve su página 503
                                ~265ms (sano todo el incidente)      de mantenimiento/capacidad
```

El fallo está en el último salto, no en los dos primeros.

### `gateway.client.ts` — `_httpGet()` (líneas 138–148)

```ts
} catch (err) {
    if (err instanceof AxiosError && err.response) {
        // api-gateway respondió — no es un timeout ni un rechazo del circuito
        const status = err.response.status;              // 503
        if (status === 404) throw new NotFoundException('Recurso no encontrado');
        const upstream = err.response.data;               // el HTML crudo de Apache
        const body = upstream && typeof upstream === 'object'
            ? upstream
            : { statusCode: status, message: upstream ?? `Error del api-gateway (${status})` };
        throw new HttpException(body, status);            // upstream no es objeto -> message = HTML completo
    }
    throw err;
}
```

Ese `HttpException` sube hasta `handleFallback`, que solo reescribe el mensaje cuando el error es `CircuitBreakerOpenError`; para cualquier otro error de infraestructura lo relanza intacto (`throw err`) — de ahí que el HTML llegue sin filtrar hasta el log y hasta el cliente.

## Hipótesis descartadas

| Origen candidato | Mensaje que habría producido | Veredicto |
|---|---|---|
| Circuit breaker (fallback custom) | `"api-gateway no disponible (circuit open)"` | Descartado |
| Bulkhead HTTP global | `"Request timed out waiting for processing."` | Descartado |
| Apache delante de `api-middleware-service` caído | Misma página HTML, pero con fallo de conexión (no `duration≈265ms` consistente) | Descartado |
| Apache delante de `api-gateway`, upstream real caído | Página 503 por defecto de Apache reenviada dentro del `message` | **Confirmado** |

## Acciones

- [x] **Timeout de axios 5000ms → 3000ms** (`gateway.client.ts:135`). Mitiga el escenario de downstream *colgado* sin responder — no aplica a este incidente puntual, donde Apache respondió rápido con un 503 real.
- [ ] **No reenviar HTML crudo en `message`.** En `_httpGet`, cuando `upstream` no sea JSON, construir un mensaje genérico (p. ej. `"Error del api-gateway (503)"`) en vez de volcar el body tal cual.
- [ ] **Alertar sobre `OPEN` sostenido del circuito.** El `onStateChange` de `api-gateway` ya loguea las transiciones — falta engancharlo a una alerta cuando el circuito permanece `OPEN` más de N ciclos, para detectar este tipo de caída sin depender de un script manual.
